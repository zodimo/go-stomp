## Dev Notes

### Previous Story Context
From Story 2.3: Successfully implemented operation synchronization with a centralized frame router. All operations now use the frame router instead of individual readers, and there's proper timeout handling and thread-safe access to pending operations. However, there's still a critical race condition between when frames are sent and when operations are registered.

### Current Implementation Issues
The current implementation has a critical race condition where frames are sent to the server before the corresponding pending operation is registered with the frame router. This creates a timing issue where the server's RECEIPT response may arrive before the operation is ready to handle it, causing timeouts and missed callbacks.

```go
// Current problematic flow:
func (c *CallbackConn) Send(...) {
    // 1. Create frame
    // 2. Send frame to server
    // 3. Register operation with receipt handler
    // 4. Wait for receipt (which might have already arrived and been discarded)
}
```

### Required Implementation Pattern
The solution requires reversing this order to ensure operations are registered before frames are sent:

```go
// Correct flow:
func (c *CallbackConn) Send(...) {
    // 1. Create frame
    // 2. Register operation with receipt handler
    // 3. Send frame to server
    // 4. Wait for receipt (which will now be properly routed)
}
```

### Disconnect Operation Issues
The disconnect operation has specific issues with state transitions:
- Frame reader may be stopped before receipt is received
- Connection state may be stuck in "Disconnecting" state
- Callbacks may not be triggered properly
